## Пользовательские сценарии

### Организатор

1. Открывает «Создать событие» на главной (`/calendars/new` или `/organizer/event-types/new`).
2. Вводит название, описание и длительность. Сервер создаёт постоянный случайный Id (UUID v4 без дефисов, 32 строчных шестнадцатеричных символа).
3. Нажимает «Скопировать ссылку» после создания или в разделе «События» (`/event-types`) и отправляет гостю абсолютную ссылку на отдельное событие `/event-types/{id}`. Страница организатора остаётся открытой. При ошибке буфера обмена доступно поле для ручного копирования.
4. Может создавать несколько форматов встреч в одном календаре. Одинаковые названия разрешены: каждое создание получает отдельный адрес.
5. Открывает «Предстоящие встречи» (`/organizer/bookings`) и видит встречи всех событий в одном
   хронологическом списке: начало, окончание, часовой пояс с UTC offset и контакты гостя.
   Начавшиеся встречи скрыты; начало ровно сейчас включается. Список включает все будущие встречи без ограничения по дате.
   Пустой список, загрузка и ошибки имеют отдельные состояния; доступна ручная перезагрузка.
6. Создание событий, раздел «События» и список встреч доступны всем без входа.

Раздел «События» служит организатору для просмотра событий и получения ссылок для гостей.
Он показывает события в порядке id: название, описание, длительность и кнопку копирования
ссылки. Есть состояния загрузки, ошибки и пустого списка. В учебном демо раздел
общедоступен; разделение сценариев не ограничивает доступ.

После создания появляется подтверждение «Событие создано» и ссылка «К событиям».

### Гость

Организатор отправляет гостю ссылку `/event-types/{id}`. Гостевая страница содержит
логотип без ссылки, описание, календарь, форму и подтверждение; меню управления,
списка событий и возврата нет во всех состояниях страницы. Это разделение сценариев,
а не ограничение доступа. Гость открывает календарь выбранного события, в том числе
напрямую и после обновления страницы. Календарь показывает все 14 локальных дат,
название, описание, длительность и часовой пояс. Можно выбрать дату и свободное время,
проверить начало и окончание в часовом поясе календаря. Для нерабочих дат и отсутствия
свободного времени есть отдельные сообщения. При возвращении на страницу и смене локальной
даты свободное время обновляется; недоступный выбор сбрасывается с объяснением.

После выбора гость вводит имя, email и необязательный комментарий, подтверждает запись
и видит название, дату, начало, окончание и часовой пояс сохранённой встречи.
Занятость общая для всех событий: время, пересекающееся с подтверждённой встречей, становится недоступным.
Если выбранное время успели занять, выбор сбрасывается, свободное время обновляется,
контакты сохраняются для повторной записи. После сетевой ошибки предлагается обновить
свободное время: отсутствие ответа не означает, что запись не сохранилась.
После успешной записи список встреч организатора обновляется при возвращении на страницу.

### Границы первой версии

- Один организатор, один общий календарь и несколько событий с общей занятостью.
- Будни 09:00–18:00, timezone `Europe/Moscow`, ближайшие 14 локальных дат и старты через 30 минут.
- Общедоступное учебное демо без авторизации; используются вымышленные контакты.
- Любой посетитель может создавать события и просматривать список встреч с контактами гостей.
- Нет редактирования событий и расписания, отмены и переноса встреч.
- Нет внешних календарей, отправки писем и автоматического создания видеозвонков.

## Стек

- React, TypeScript, Vite и TanStack Query; HTTP-запросы через сгенерированный Fetch SDK.
- TypeSpec → OpenAPI 3.1 → Orval / datamodel-code-generator → TypeScript SDK / Pydantic 2.
- Python, FastAPI, SQLAlchemy asyncio, psycopg 3, PostgreSQL и Alembic.
- mise управляет версиями инструментов и задачами, uv — Python-зависимостями, npm — JS-зависимостями.

Реализованы статичная главная, форма создания типа события, PostgreSQL-хранилище,
публичный каталог, выбор времени, бронирование без пересечений и общий список встреч. Главная и пустая форма открываются без API;
отправка формы, каталог и календарь типа требуют сервер и БД. Старый путь
`/calendars/new` открывает рабочую форму.

API-контракт: `POST /api/organizer/event-types` (публичный, `201`),
`GET /api/event-types` (публичный, `200`),
`GET /api/event-types/{eventTypeId}/slots` (публичный, `200` с метаданными типа, timezone,
границами окна и 14 датами; неизвестный тип — `404 EVENT_TYPE_NOT_FOUND`).
`GET /api/organizer/bookings` (публичный, `200`) возвращает `items` всех типов с
`startsAt >= now`, в порядке начала и затем UUID, без фильтров, пагинации и границы
14 дней. В строке — UUID, метаданные типа, `startsAt`, `endsAt`, `timezone`, `guest`
с именем, email и комментарием. Ответы управления, включая ошибки, имеют
`Cache-Control: private, no-store`; SDK также запрашивает список без HTTP-кэша.
`POST /api/bookings` публично принимает `eventTypeId`, `startsAt` с обязательным offset
и `guest` с `name`, `email`, необязательным `comment`; возвращает `201` с UUID,
метаданными типа, началом, окончанием и timezone после commit. Имя после trim —
1–120 символов, email — до 254, комментарий — до 2000. Окончание вычисляет сервер.
`409 TIME_CONFLICT` означает пересечение, `422 SLOT_NOT_BOOKABLE` — устаревший
или недопустимый по расписанию старт. Публичного чтения брони по UUID нет;
каталог и свободные слоты не раскрывают контакты и идентификаторы чужих броней.

Моменты ответа нормализованы к UTC с `Z`; локальные даты передаются отдельно.
Сегодня допускаются только старты строго позже серверного времени; длительность
считается в реальных минутах. Несуществующие локальные старты пропускаются, повторённые
сохраняются отдельно и отображаются с offset. Новые Id генерирует сервер при создании; клиент не передаёт `id` в POST.
Старые строковые Id, ссылки и бронирования сохраняются без миграции.
При коллизии первичного ключа сервер делает до трёх попыток; исчерпание даёт `500 INTERNAL_ERROR`. Название после trim: 1–120 символов,
описание: до 2000 (пустое допустимо), длительность: целое число 1–540 минут.
Ошибки содержат `code` и `message`: `422 VALIDATION_ERROR`, `503 DATABASE_UNAVAILABLE`,
`500 INTERNAL_ERROR`. Необъявленные поля запрещены.

Страница проверки подключения удалена; страницы `/status` нет. Диагностический
API `GET /api/health`, его сгенерированный SDK и тесты сохранены. Сервер проверяет
PostgreSQL запросом `SELECT 1`: при доступной БД API возвращает `200`, при ошибке
подключения — `503` с публичным кодом `DATABASE_UNAVAILABLE`. Для проверки API и
интеграционных проверок требуется окружение, описанное в разделах ниже.

## Структура

```text
api/main.tsp                  # Источник API-контракта
api/generated/openapi.yaml    # Сгенерированный OpenAPI 3.1
backend/app/                  # Приложение FastAPI, настройки, async-сессии
backend/app/generated/        # Сгенерированные транспортные модели Pydantic
backend/migrations/           # Миграции Alembic
backend/tests/                # Тесты API, контракта и PostgreSQL
frontend/src/                 # React-приложение
frontend/src/api/generated/   # Сгенерированный Fetch SDK и Query-хуки
frontend/e2e/                 # Быстрые браузерные проверки и отдельный full-stack профиль
scripts/generate.mjs          # Генерация и проверка её актуальности
mise.toml                     # Версии инструментов и общие задачи
compose.yaml                  # PostgreSQL для локальной разработки и CI
```

Один корневой [package.json](./package.json) содержит зависимости фронтенда и
JS-генераторов; один [pyproject.toml](./pyproject.toml) — зависимости бэкенда и
Python-инструментов. Lock-файлы сохранены в репозитории.

В `package.json` заданы временные `overrides` для исправленных версий `undici`
и `minimatch` в зависимостях генераторов и линтеров. При обновлении этих
инструментов проверьте, нужны ли переопределения; совместимость проверяется
общей задачей `check`.

## Установка

Предварительно установите [mise](https://mise.jdx.dev/getting-started.html) версии
2026.10.25 или новее и Docker с Compose v2. Docker Engine должен быть запущен.
Для команд из примеров требуется POSIX-оболочка (macOS/Linux).

В [mise.toml](./mise.toml) закреплены Python **3.13.18**, Node.js **24.22.2** и uv
**0.13.6**. PostgreSQL закреплён как `postgres:17.11-bookworm`.

```bash
git clone https://github.com/danilaKazimir/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
cp .env.example .env
mise run setup
```

`setup` выполняет `uv sync --frozen`, `npm ci`, `mise run test:e2e:install`
и `mise run hooks:install`. Задача `test:e2e:install` скачивает версию Chromium,
закреплённую Playwright; на Linux она также может установить системные зависимости
браузера.
Задача `hooks:install` задаёт локальный `core.hooksPath=.githooks` для этого репозитория.
Виртуальное окружение `.venv`
создаётся с явным указанием Python из mise; загрузка другого Python через uv
отключена. Локальные переменные из `.env` подхватывает mise. Файл не коммитится.

В уже настроенном окружении после добавления Playwright установите зависимости
и браузер:

```bash
npm ci
mise run test:e2e:install
```

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_USER` | Пользователь PostgreSQL, по умолчанию `calendar` |
| `POSTGRES_PASSWORD` | Пароль локальной БД, по умолчанию `calendar` |
| `POSTGRES_DB` | База приложения, по умолчанию `calendar` |
| `POSTGRES_PORT` | Порт PostgreSQL на хосте, по умолчанию `5432` |
| `DATABASE_URL` | SQLAlchemy URL с драйвером `postgresql+psycopg` |
| `TEST_DATABASE_URL` | URL отдельной тестовой БД, имя должно оканчиваться на `_test` |
| `API_PROXY_TARGET` | Адрес FastAPI для прокси Vite, по умолчанию `http://127.0.0.1:8000` |

При изменении пользователя, пароля, имени БД или порта согласуйте оба URL с
настройками Compose. Значения `POSTGRES_*` применяются при первом создании volume;
изменение `.env` не меняет пользователей и базы в существующем volume.

## Использование

Настройка ключа или вход не требуются.

```bash
mise run db:up
mise run migrate
mise run dev
```

Фронтенд: <http://127.0.0.1:5173>. API: <http://127.0.0.1:8000/api/health>.
Интерактивная документация FastAPI: <http://127.0.0.1:8000/docs>.
Vite проксирует `/api` на бэкенд, поэтому локальному фронтенду не требуется CORS.
`Ctrl-C` останавливает оба процесса разработки; завершение одного процесса
останавливает второй. База продолжает работать.

```bash
mise run db:down
```

Эта команда останавливает PostgreSQL и сохраняет данные в volume. Бэкенд и миграции
используют асинхронный драйвер psycopg; на каждый запрос создаётся отдельная
`AsyncSession`, а при остановке API освобождается пул соединений.

## Генерация API

```bash
mise run generate
mise run generate:check
```

Источник истины — [TypeSpec](./api/main.tsp). Версия OpenAPI 3.1 задана явно в
[настройках эмиттера](./api/tspconfig.yaml). Orval и datamodel-code-generator
читают один и тот же [OpenAPI-документ](./api/generated/openapi.yaml).
Сгенерированные файлы сохраняются в Git и вручную не редактируются.

Проверка актуальности генерирует результаты во временном каталоге и сравнивает
сохранённые файлы побайтово, включая добавленные и удалённые файлы. Рабочие
сгенерированные файлы при проверке не перезаписываются. Ошибки HTTP передаются
из Fetch SDK в TanStack Query со статусом и телом ответа.

Обработчики, бизнес-логика и ORM-модели пишутся вручную. Любое изменение структуры
БД оформляется новой миграцией. Начальная миграция фиксирует историю Alembic и
пока не создаёт предметных таблиц.

## Проверки

Перед каждым коммитом Git-хук `pre-commit` запускает `mise run lint`: Ruff,
проверку форматирования Python и ESLint. Проверяется весь рабочий каталог,
включая изменения, ещё не добавленные в индекс; файлы автоматически не исправляются.
Ошибка блокирует коммит. Хук не требует PostgreSQL. Полная проверка остаётся
в `mise run check` и CI.

Для уже настроенного окружения подключите хук один раз:

```bash
mise run hooks:install
```

Проверки можно запустить вручную командой `mise run lint`.

Создайте отдельную тестовую БД. Для значений из `.env.example`:

```bash
mise run db:up
docker compose exec -T db createdb -U calendar calendar_test
mise run check
```

`createdb` выполняется один раз. Для повторных проверок достаточно `mise run check`.
Интеграционные тесты требуют `TEST_DATABASE_URL`, отличный от `DATABASE_URL`, и
имя БД с суффиксом `_test`. При отсутствии настройки тесты завершаются ошибкой,
а не пропускаются. Тест миграций выполняет downgrade/upgrade в тестовой БД.

Общая проверка включает Ruff, mypy, ESLint, TypeScript, pytest, Vitest, сборку Vite,
актуальность генерации, браузерные тесты Playwright и HTTP smoke-тест запуска.
Тесты проверяют реальные HTTP-запросы и ответы по каноническому TypeSpec-контракту,
создание типов, каталог, общедоступный список встреч, валидацию, уникальность автоматически созданных адресов и сохранность после
перезапуска приложения. Проверяются миграции в обе стороны, ограничения хранения,
health, параллельные запросы и отдельные сессии, отсутствие деталей подключения в `503`. Тесты SDK проверяют
успех, HTTP-ошибку в состоянии Query, не-JSON ответ и отмену запроса.

```bash
mise run test:unit         # Без PostgreSQL
mise run test:integration  # Только проверки PostgreSQL и миграций
mise run test:e2e          # Быстрые браузерные проверки без API и PostgreSQL
mise run test:e2e:full      # Полный цикл до списка организатора с API и PostgreSQL
mise run test:smoke        # Запуск реальных FastAPI и Vite, проверка HTTP
```

Для `test:e2e` нужны установленные npm-зависимости и Chromium из
`mise run test:e2e:install`. Playwright сам запускает Vite на
`127.0.0.1:15174`; этот отдельный порт должен быть свободен. Тесты выполняются
в headless Chromium без запущенных API и PostgreSQL и проверяют переходы между
главной страницей и формой `/calendars/new`, навигацию с клавиатуры и
расположение элементов на мобильном экране; каталог проверяется на загрузку,
ошибку с повтором и пустое состояние. Сценарии находятся в `frontend/e2e/`.

`test:e2e:full` использует `playwright.full.config.ts`, отдельную тестовую БД из
`TEST_DATABASE_URL` (суффикс `_test`, отличается от `DATABASE_URL`), применяет миграции,
очищает типы и бронирования в этой тестовой БД
и запускает FastAPI на `127.0.0.1:18001`, Vite на `127.0.0.1:15175`. Порты должны
быть свободны. Проверяются создание типов без ключа, каталог, сохранение полей при ошибке отправки, мобильная клавиатура, прямая гостевая ссылка без навигации,
бронирование и конфликт с сохранением контактов, общедоступный список встреч
и обновление страницы.
Основной путь использует настоящие API и PostgreSQL; отдельные состояния страницы
(пустое окно, повторённые часы, ошибки и смена даты) проверяются с фиксированными
HTTP-ответами на границе браузера. Процессы завершаются автоматически; тестовые типы с уникальными id остаются в
выделенной БД. Не запускайте этот профиль параллельно с PostgreSQL-тестами:
они очищают данные, меняют тестовый timezone и проверяют downgrade миграций.
Оба браузерных профиля включены в `mise run check`.

Для `test:smoke` нужны установленные зависимости, запущенный PostgreSQL
(`mise run db:up`) и существующая отдельная БД из `TEST_DATABASE_URL` с суффиксом
`_test`, отличная от `DATABASE_URL`. Создайте её командой `createdb` из примера
выше. Smoke-тест сам применяет миграции к тестовой БД, запускает Uvicorn без
перезагрузки на `127.0.0.1:18000` и Vite на `127.0.0.1:15173`; оба порта должны
быть свободны. На ожидание готовности отводится 30 секунд.

Проверка подтверждает успешный ответ `/api/health` напрямую и через прокси Vite,
а также выдачу HTML главной страницы. Она выполняется без браузера и не проверяет
исполнение React. После успеха, ошибки или прерывания smoke-тест завершает
запущенные им процессы; PostgreSQL продолжает работать, тестовая БД сохраняется.

Собственный [CI](./.github/workflows/check.yml) устанавливает инструменты из mise,
выполняет `mise run setup`, поднимает PostgreSQL через тот же Compose и запускает
`mise run check`. Учебный workflow Хекслета сохранён отдельно.

HTTP/PG-проверки календаря используют фиксируемый серверный источник времени без
публичного отладочного API: проверяются границы дня и окна, длительности,
прошедшие старты, DST и исторические пропущенные/повторённые рабочие даты.
Playwright проверяет выбор с клавиатуры и на мобильном экране, прямую ссылку,
пустые состояния, обновление окна в timezone календаря и подписи повторённых часов.
HTTP/PG-тесты проверяют бронирование, пересечения разных типов, смежные интервалы,
отсутствие чужих контактов в календаре и валидацию. Конкурентные HTTP-запросы ждут общую блокировку на разных
PostgreSQL-соединениях до освобождения ресурса: выигрывает ровно одна пересекающаяся
запись, смежные успешны обе; общедоступный GET подтверждает точное число сохранённых встреч
и контакты. Список проверяется на границу текущего момента и отсутствие верхнего окна.
Время фиксируется после ожидания блокировки.
Отдельная проверка прямого SQL подтверждает немедленное GiST exclusion constraint
по полуоткрытому диапазону, конечные обязательные timestamps и положительный интервал.
Транзакции работают в READ COMMITTED, первой берут общую строку календаря FOR UPDATE,
затем отдельным запросом проверяют пересечения. После rollback только SQLSTATE 23P01
с именем ограничения занятости превращается в TIME_CONFLICT.

## О Хекслете

[Хекслет](https://ru.hexlet.io/) — школа программирования: авторские программы обучения с практикой, поддержкой наставников и реальными проектами, которые остаются в резюме. Этот репозиторий — один из таких проектов.

## Docker и Render

```bash
docker build --platform linux/amd64 -t call-calendar .
docker run --rm --memory=512m -e PORT=10000 -p 10000:10000 call-calendar
```

Контейнер автоматически создаёт PostgreSQL, применяет миграции, добавляет
событие «Знакомство» на 30 минут и запускает приложение на `0.0.0.0:$PORT`
(по умолчанию 10000). Событие сразу доступно в каталоге и сохраняет адрес
`/event-types/d0c5f4b98ee747c8b777a63314ef0475` при каждом запуске.
**Данные встроенной БД сбрасываются при каждом запуске контейнера**, включая
перезапуск, деплой и пробуждение Render Free после засыпания. Локальная БД
Compose не затрагивается. При переданном `DATABASE_URL` используется внешняя
PostgreSQL с её собственным каталогом; формат URL — `postgresql+psycopg://...`.

Render: Docker Web Service, ветка `main`, регион Frankfurt, тариф Free,
Dockerfile в корне; команду запуска переопределять не нужно.
Попробуйте [записаться на «Знакомство»](https://call-calendar-danilakazimir.onrender.com/event-types/d0c5f4b98ee747c8b777a63314ef0475) с вымышленными контактами.
**Данные демо сбрасываются при перезапуске, деплое и пробуждении Render Free.**

Безопасный шаблон MCP: `codex-mcp.example.toml`. Перенесите его секцию в
локальную конфигурацию Codex и выполните `codex mcp login render` для OAuth.
Альтернатива — `bearer_token_env_var = "RENDER_API_KEY"`; ключ передаётся в
окружении процесса Codex и никогда не сохраняется в репозитории.

Проверка готового сервиса без очистки БД (создаёт вымышленные встречи):

```bash
DEPLOYMENT_URL=http://localhost:10000 mise exec -- npm exec -- playwright test --config playwright.deployment.config.ts
```
